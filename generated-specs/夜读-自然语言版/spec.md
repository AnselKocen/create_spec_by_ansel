## 【用户需求描述】 ← 唯一的填空,也是整份 spec 的方向盘

我想做一个「夜里被读故事」的产品。氛围像一档深夜电台:声音是温柔的,但故事本身有重量。用户不是在"玩游戏",而是被一个温和的声音带着,一段一段往下读。

每读到一个关键处,故事会停下来,把选择交给用户。但我要的选择**不是"对 / 错",不是"好结局 / 坏结局",而是取舍**——两边都有道理,选了一边就失去另一边,而且**这个"失去"会被故事记住**,过一阵子用它自己的方式提一句。

我不要分数,不要血条,不要成就弹窗,不要"恭喜通关"。结局**不评判**用户选得好不好,只是把一路的取舍收拢成一种**回响**:你成了一个什么样的人,故事用它自己的语气说回给你听。

节奏要慢。一屏只放一口气的量,不要把整章塞满。翻页要轻,像翻一本旧书。整件事应该让人在睡前**愿意读一段**,而不是让人想"再刷一把"。

故事的具体内容我会用 skills 喂进来——可能是一个少年的一夜,也可能是一段旧关系的复盘。框架不挑题材,但上面这种"**温柔、有重量、选择是取舍、结局是回响**"的气质必须保住。

> 下面所有内容,都是对这段描述的扩展与设计。

## 这是什么

夜读是一个**沉浸式分支叙事阅读框架**。它把一篇带分支的故事,变成一段"被读给你听"的夜间体验:大段时间里用户只是安静地往下读,偶尔在一个停顿处,替故事里的人做一次取舍;读到最后,这些取舍不会变成一个分数,而是收拢成一段对着用户说的结语。

它服务的是那种**睡前想被一个故事接住一下**的人——不想被关卡、计时、连胜推着走,只想读点有重量但温柔的东西。成功的样子很具体:用户读完愿意安静坐一会儿,而不是马上点"再来一局"。

## 怎么玩(核心循环)

核心循环只有一句话:**读一段 → 偶尔遇到一个停顿 → 做一次取舍 → 故事记下你给的和你放弃的 → 继续读,直到所有取舍收拢成一个结局。**

把它拆开来设计:

- **段(beat)**:阅读的最小单位,一屏一段,只放"一口气"的量(正文可见量建议 ≤ 180 字)。读完轻点继续,**手动推进,绝不自动滚屏**。段的文本来自 skills。
- **停顿(选择点)**:不是每段都有,只在关键处出现,让停顿显得珍贵。一个停顿给 2 个取舍,**两个都是合理的**,文案上不许暗示哪个"更好"。选择点和它的两个选项来自 skills。
- **取舍如何被记住**:这是从需求描述里"失去会被故事记住"长出来的核心设计。我**不用分支树**(分支树会指数爆炸,也留不住气质),而是用一组 **2–3 条隐藏的倾向轴**(抽象成"留 / 走""说 / 藏""近 / 远"这类对立轴,具体语义由 skills 定义)。每做一次取舍:① 往某条轴上累加;② **同时记下"被放弃的那一边"**,存成一句"回声素材"。故事在后面合适的段落,会把这句回声轻轻还给用户(例如某段的可选插入句),让"失去"真的留下痕迹。
- **结局(回响)**:读到末尾,用**几条倾向轴的最终组合**去匹配一个结局,而不是用对错或分数。结局是一段**第二人称的反射式收束**——"你最终成了一个会……的人"——语气由 skills 的结局文本决定,**不打分、不弹成就**。结局集合(通常 3–5 个)来自 skills。

这套循环刻意没有的东西(全部来自需求描述的禁忌):没有分数、血条、计时、连胜、成就弹窗、"通关"字样。回看与重读是允许的,但**不鼓励"刷"**——没有任何为重复游玩设计的奖励。

## skills 怎么长进来(内容契约)

> 完整内容文件会与本 spec 一起提供,通常位于项目根目录的 `skills/` 文件夹中。构建产品时,必须读取每个文件的**完整内容**,并从中提取本 spec 需要的内容,不能只看摘要或标题。核心叙事必须能追溯到 skills 原文。

| 内容文件路径 | 覆盖模块 | 在本产品中的用途 |
|-------------|----------|------------------|
| `{{CONTENT_FILE_PATH}}` | 故事正文 / 分支 / 结局 | 段落文本、停顿处的取舍、倾向轴语义、结局回响文本、插画 prompt 素材 |

实现时从 skills 里**提取并映射**:

- 故事的**分段** → 一屏一段的 beat 序列(注意保住"一口气"的节奏,过长的原文要拆段,不要塞满)。
- 故事里的**关键抉择 / 冲突** → 停顿处的取舍(每处 2 个都合理的选项)。
- 抉择背后的**价值对立** → 2–3 条隐藏倾向轴的语义。
- 每个取舍**被放弃的一边** → 一句"回声素材",供后文回还。
- 故事的**几种走向 / 收束** → 结局回响文本与匹配规则。
- 每章关键**场景 / 意象** → 章节插画的 prompt 素材。

## 长成什么样(视觉与气质)

这是一个**以排版和氛围取胜**的产品,核心视觉不是数据图,而是"夜里灯下读一本书"的感觉:

- **基调**:低照度暖色,像台灯打在纸上。深夜蓝灰底 + 暖纸色阅读区 + 一圈柔和的灯晕。对比要克制,别刺眼——它是睡前读物。
- **排版即设计**:正文是主角。讲究字号、行距、段距、首行节奏,一屏一段的留白要舍得。标题不是普通 `h1`,而是带夜读气质的题字。
- **轻 UI(SVG / CSS)**:推进、章节、进度都做成**贴合叙事**的样子——例如灯晕呼吸、纸页边缘、把进度藏成一根渐亮的灯丝,而不是一条游戏进度条。按钮 / 选项卡片都要主题化,hover / active 有轻反馈。
- **动效**:翻页轻、淡入淡出,**绝不瞬切**;选择确认时有一下温柔的回应。`prefers-reduced-motion` 下关闭灯晕呼吸、漂浮等装饰,**保留**淡入淡出这类承载阅读节奏的核心过渡。

> 本产品核心视觉是排版与氛围,**不触发** `specforge/modules/svg-css-visual-primitives.md`(那是给图表 / 地图 / 机制图 / 互动模拟的绘制手册)。若 skills 内容改成需要结构图、地图或参数模拟,则必须按该模块补专项绘制指南,不能只写"高精度 SVG"。

## 图片(资产契约 —— 引用,不复述)

本产品图片**严格遵守 `specforge/modules/image-generation-rules.md` 的完整契约**,包括:`first-run-cache` 时机、资产准备页、required 图片预生成 / 预加载闸门、IndexedDB Blob 缓存与缓存记录、`IMAGE_ASSET_MANIFEST` / `IMAGE_ASSET_RUNTIME_STATE` 三层状态、生图返回 URL 时的可读取性与 MIME/load/decode 校验、`http://.../__runtime/llm-images/...` 这类 runtime 临时 URL 必须先规范化为 HTTPS / 同源相对 URL 再转 Blob、cache hit 不调用生图 API、localStorage 不存图片、以及任意 required 或 optional 图片失败 / 超时 / 用户取消时进入**显式无图片兜底体验**(失败资产保持 `failed` / `ready=false` 并保留重试)。以上不在此复述,以模块原文为准。

下面只写**本产品特有的部分**:

**统一画风基底(STYLE_PROMPT_BASE)**:`warm low-light storybook illustration, muted lamplight palette, soft painterly grain, intimate nighttime mood, gentle rim light, quiet and unhurried`(所有图片共用,保证画风统一)。

**IMAGE_ASSET_MANIFEST(本产品资产)**:

| asset_id | 用途 | required | 说明 |
|----------|------|----------|------|
| `title_bg` | 标题页夜读氛围背景 | 是 | 进入即见,必须预生成 |
| `chapter_illus_{n}` | 每章入口关键场景插画 | 是 | 每章 1 张,数量 = skills 章节数 |
| `ending_cg_{k}` | 每个结局的回响画面 | 是 | 数量 = skills 结局数(通常 3–5),**全部预生成** |
| `segment_inline_{m}` | 段内点缀小插画 | 否 | optional,可后台生成,失败则该段无图继续 |

**本产品的 required 闸门设计**:`title_bg` + 全部 `chapter_illus` + 全部 `ending_cg` 为 required,在进入正常阅读体验前一次性预生成并 ready。**为什么结局 CG 也全做 required**:契约禁止"逐页 / 临到才生成 required 图片",而最终只会抵达其中一个结局却事先不知是哪个,所以把**有界的结局集合**整批预生成,是被契约推着做出的设计,不是浪费。`segment_inline` 走 optional,不阻塞阅读。

## 数据与状态(轻量)

- **运行时进度(localStorage,只存轻量)**:当前段索引、几条倾向轴的当前值、已记录的"回声素材"、已抵达的结局。**不存图片、不存 base64、不存 object URL。**
- **图片资产**:`IMAGE_ASSET_RUNTIME_STATE` + IndexedDB 缓存记录,按引用契约执行;展示时从 IndexedDB Blob 现取并 `createObjectURL`,object URL 只用于本次会话。
- **构建 / 填充阶段产物**:从 skills 提取的段序列、选择点、倾向轴语义、结局规则、插画 prompt —— 这是"长出产品"的数据,与上面的运行时进度分开。

## 护栏与验收(coverage checklist —— 下限保护)

这张清单既是**覆盖保证**,也是**验收口径**。过不了就算没写完——它替代了旧模板用 16 章强制的"别漏项"。

- [ ] 核心循环讲清:读 → 取舍 → 记下"给的"和"放弃的" → 回响结局,且**不用分支树**而用倾向轴。
- [ ] skills 映射可追溯:段落、选择点、倾向轴、结局、插画 prompt 都能指回 skills 原文;实现者读了**全文**而非摘要。
- [ ] 图片走完整契约:first-run-cache、required 闸门(标题 + 全部章节图 + 全部结局图预生成)、无图片兜底、IndexedDB Blob、URL 可读取性校验、runtime 临时 URL 规范化;**没有用 CSS/SVG/Canvas/emoji 伪装生图**。
- [ ] 准确性 = fantasy:不做事实校验,但故事**内在一致**、气质一致。
- [ ] 视觉:排版与氛围达标,标题非普通 h1,UI 主题化;`prefers-reduced-motion` 下保留淡入淡出等核心过渡、关闭装饰动效。
- [ ] 忠于需求描述的禁忌:**没有**分数 / 血条 / 计时 / 连胜 / 成就弹窗 / "通关"字样;选项文案不暗示对错;结局不评判。
- [ ] 节奏:一屏一段、手动推进、不自动滚屏、无"再刷一把"的奖励结构。

## 给实现模型的一段话(扩展指令 —— 防注水)

把上面的 **【用户需求描述】当作意图的唯一真源**:拿不准任何设计时,优先服从那段话的语气和取舍观,而不是机械套结构。用 **skills 内容坐实**每一处具体文本与分支,读全、读透,别拿摘要凑。在**引用的契约**(生图、reduced-motion、数据存储)边界内做**真正的设计决策**——核心循环细节、倾向轴语义、回声如何回还、结局如何收束——而**不要复述本文档、不要为了"看起来完整"而注水**。这份 spec 的篇幅本来就该比内容少:它给方向和护栏,故事的血肉在 skills 里,产品的设计在你手上。
