# 通用游戏 · 自然语言版 spec

> 这是一份**一句话造游戏的框架**。整份文档只有一个真正的填空——下面的 **【用户需求描述】**,它**保持为空**,由用户在使用时填一句自然语言(例如"帮我做个 xxx 游戏,我希望 xxxx")。除此之外,本文档**不锁定任何玩法、主题、美术**;它固定的只是"怎么把**任意**一句话变成一个做得好的游戏"的指导。
>
> 本框架**不依赖 skills 内容文件、不使用任何真实图片**。结构沿用 SpecForge,但以**引用**和**清单**形式存在,不复述契约全文。收到用户那句话后,先锁设计,再开始做;任何地方与【用户需求描述】冲突,以【用户需求描述】为准。

---

## 这是什么

一台游戏制造机。用户只给你**一句自然语言**——他想要什么样的游戏、希望有什么体验。你的工作:**从这一句话里,设计并做出一整个游戏**——玩法、机制、主题、美术、手感全部从这句话长出来。这份 spec 不替用户决定做什么游戏,只保证:无论他说的是赛车、塔防、解谜还是种田,做出来的都是一个**玩法立得住、画面有风格、操作有反馈**的完整游戏,而不是个能跑的半成品。

## 【用户需求描述】 ← 唯一的填空(保持为空,由用户填)

```
帮我做个 ⟨什么样⟩ 的游戏。我希望 ⟨核心玩法 / 想要的体验 / 特别要求 / 画风或氛围⟩。
```

用户实际会这样填(都合法,框架对它们一视同仁):

- "帮我做个**赛车**游戏,我希望能**漂移、放氮气**,**赛博朋克霓虹夜景**。"
- "帮我做个**塔防**,我希望**塔能合成升级**,走**可爱手绘风**。"
- "帮我做个**解谜**游戏,推箱子那种,但**每关重力方向会变**。"
- "帮我做个**种田**游戏,我希望**节奏很慢、很治愈**,**有四季**。"

这一句话是**唯一真源**:

- **用户说了的**(类型、特别玩法、画风、氛围、特别要求)→ 必须照做,不许擅自改成别的。
- **用户没说的**(核心循环细节、数值、关卡、UI、粒子、难度曲线)→ **你来设计**,但要服从他那句话的语气和取向。
- 别把他的话"标准化"成模板腔——他怎么说的,那股劲儿要落到游戏里。

> 下面所有内容,都是"拿到这句话之后该怎么做"。

## 第一步:先把游戏从那句话里"读出来"(开做前必须锁定)

这是本框架的核心动作,也是 SpecForge"**先锁玩法,再动手**"的体现。**写第一行代码前**,先从【用户需求描述】里把下面这些定下来(用户说了的照搬,没说的你设计):

- **类型 / 视角 / 实时性**:横版?俯视?回合还是实时?(从词里读,或合理推断)
- **核心循环**:玩家每一轮具体做什么 → 系统怎么反馈 → 怎么推进。一句话能说清。
- **2–3 个核心机制**:撑起玩法的支柱,缺一个游戏就垮(例:漂移 + 氮气 + 赛道;或 建塔 + 合成 + 波次)。
- **胜负 / 进度 / 反馈**:怎么赢、怎么输、怎么知道自己在变强。
- **主题与氛围**:这决定后面**一切视觉**,从用户的画风词或题材推。
- **操控**:键盘 / 鼠标 / 触屏 / 组合,跟类型匹配。
- **难度与规模**:有几关 / 多少波 / 怎么变难,单局多长。

把这些锁死后再开做。拿不准的地方,优先服从那句话的气质,而不是套一个"标准游戏"。

## 玩法该长成什么样(通用质量基线)

不管做的是哪种游戏,玩法都要满足:

- **核心循环跑得通、没有死局**:从开始界面出发,不改代码就能玩到赢 / 结束,不存在必死、卡死、按钮失效。
- **机制互相咬合**:核心机制之间有关系,不是各玩各的;深度来自机制交互,不是堆数值。
- **胜负清晰、进度可感**:玩家明确知道赢没赢、强没强。
- **每个操作都有即时反馈**:跳、打、捡、放、合成……做了就有视觉 / 位移 / 特效回应。没反馈的操作等于没生效。

## 长什么样(视觉 —— 从主题推导)

> 视觉 / UI / 粒子 / 动效的质量基线沿用 `spec_通用游戏.md` 的标准,不在此复述。下面是"怎么针对这一句话的主题去做"。

- **先定艺术风格**:从用户的题材 / 画风词出发,按**媒介、情绪、材质、光影、构图**组合出一套风格(像素、扁平、玻璃拟态、酸性、暗黑、手绘、复古未来……都行),**不要套默认配色**。用户给了画风就照做;没给就从题材推。
- **配色服务主题**:主色定氛围、强调色给玩家 / 关键交互、辅助色分敌人 / 道具、成功色与危险色各一;文字与背景高对比。
- **必做手感反馈(juice,适用任何游戏)**:

  | 事件 | 视觉要求 |
  |------|----------|
  | 受伤 / 死亡 | 画面短闪 + 抖动或爆炸粒子 |
  | 得分 / 拾取 | 飘字(+分)或高亮 |
  | 胜利 / 通关 | 全屏庆祝(粒子 / 放大 / 变色) |
  | 失败 / Game Over | 变灰或慢放 + 明确 UI |
  | 关键操作 | 残影 / 拖尾 / 短特效 |
  | 场景切换 | 淡入淡出或滑动,**不瞬切** |

- **动效**:移动有缓动不匀速;切换不瞬切;`prefers-reduced-motion` 下关装饰、留承载机制的核心动效;帧率目标流畅(大量粒子走 Canvas)。

## UI 与氛围(标题 / UI / 粒子 / SVG-CSS)

> 这部分是固定要的指导,沿用 `specforge/modules/ui-particles-svg.md`。

- **标题不是普通 `<h1>`**:主题化字体(发光 `text-shadow`、`background-clip: text` 渐变、描边、字距、入场动画),可配 SVG 装饰(藤蔓 / 星 / 齿轮 / 裂痕 / 像素边框,按主题)。
- **UI 全程主题化、风格统一**:按钮 / 面板 / 弹窗 / HUD 不用浏览器默认样式;从首页到游戏内到结算页质感一致,玩家不会觉得"进了另一个网页"。信息别堆角落,要有设计感。
- **氛围粒子(按主题选 1–2 种)**:花瓣 / 星闪 / 雪 / 气泡 / 萤火 / 灰烬 / 落叶 / 光斑 / 雨 / 尘埃 / 代码雨 / 音符 / 几何碎片 / 烟雾 / 像素粒子……数量 10–30,`pointer-events: none`,不挡操作,尊重 reduced-motion。
- **SVG / CSS 技巧**:角色 / 对象用 SVG path+circle+polygon + CSS 动画;图标内联 SVG 用 `currentColor`;进度条 / 血条用 SVG `stroke-dasharray`;装饰边框用 SVG path;发光用多层 `box-shadow`;质感用渐变;状态反馈结合缩放 / 位移 / 光效,不只变色。
- **如果某个游戏的核心是图表 / 地图 / 机制图 / 参数模拟**(需要标注、图例、单位、数据正确性),则额外触发 `specforge/modules/svg-css-visual-primitives.md` 的绘制手册;普通动作 / 街机 / 休闲游戏不触发,做好氛围与手感即可。

## 图片(资产契约)

本框架**不生成、不使用任何真实位图资产**:所有视觉都由 SVG / Canvas / CSS + 粒子做出来。这是刻意选择,不是降级。因此无生图、无 `IMAGE_ASSET_MANIFEST`、无首启缓存。**不得用占位图或任何方式假装这里本该有图。**

## 数据与状态

- **持久化(localStorage,轻量)**:进度 / 关卡、最高分或最佳成绩、设置(难度、reduced-motion、操控偏好);有存档时标题页显示"继续"。每次状态变化即写入。
- **运行时(不持久)**:玩家状态、敌人 / 道具 / 粒子、计时、当前关卡——活在内存与游戏循环里。
- 不存图片、base64、大字符串。

## 技术约束

- 纯前端**单文件**(HTML + CSS + JS + 内嵌 SVG / Canvas),静态打开即玩,离线可用,零依赖(字体可 CDN 带 fallback)。
- 游戏循环用 `requestAnimationFrame`;大量粒子 / 实时演算走 Canvas,UI / HUD / 标题走 HTML/CSS/SVG;现代浏览器;首屏 < 2s,帧率流畅。

## 护栏与验收(coverage checklist —— 对任何游戏都成立)

既是覆盖保证也是验收口径;过不了算没做完。它替代旧模板靠十几章强制的"别漏项"。

- [ ] **忠于那句话**:用户说的类型、特别玩法、画风、特别要求都落地了,没被擅自换成别的。
- [ ] **先锁后做**:类型 / 核心循环 / 核心机制 / 胜负 / 主题 / 操控在动手前已定,玩法立得住。
- [ ] **可玩无死局**:从开始界面出发,不改代码可玩到赢 / 结束,无必死、卡死、按钮失效。
- [ ] **机制咬合、反馈即时**:核心机制有交互深度;每个操作有即时视觉反馈。
- [ ] **视觉由主题推导**:配色 / 风格来自用户题材,非默认黑白灰;juice 表的反馈都在;切换不瞬切、移动有缓动。
- [ ] **UI 主题化**:标题非普通 h1;UI 从首页到结算风格统一;有按主题选的氛围粒子。
- [ ] **全程无图实现**:所有视觉 SVG/Canvas/CSS;没有真实图片,也没有假装该有图的占位。
- [ ] **无障碍与数据**:`prefers-reduced-motion` 适配;进度 / 最佳成绩刷新后仍在。
- [ ] **开发者亲自玩通**:从头玩到赢 / 结束,确认无死局、不卡顿、结算正确。

## 给实现模型的一段话(扩展指令 —— 防注水、防跑偏)

把 **【用户需求描述】那一句话当作意图的唯一真源**。**第一步不是写代码,是把游戏设计出来**:从那句话里锁定类型、核心循环、核心机制、胜负、主题、操控——用户说了的照做,没说的你来设计,但一切服从他那句话的语气和取向,别套一个"标准游戏"。然后在**引用的视觉 / UI / 粒子规范**(`spec_通用游戏.md`、`ui-particles-svg.md`)边界内做**真正的设计决策**,把玩法做扎实、把画面做出风格、把操作做出手感。本框架**没有 skills、没有图片**,别去读不存在的内容文件、别造图、别用占位冒充。**不要复述本文档、不要为凑结构注水**——这份 spec 只给方向和护栏,真正的游戏在你手上。最后,**亲自从头玩到赢 / 结束**,确认它真的好玩、真的是用户要的那一个。
